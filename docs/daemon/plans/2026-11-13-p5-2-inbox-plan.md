**Decisions this plan makes beyond the spec** (F2 records them):

1. **The inbox's types start in the bridge and move to the contract in Task 4.**
   Tasks 1 to 3 then never touch plan 1's files. Until Task 4, an intake item
   carries only its submission's ID. Task 4 replaces that with the whole
   submission. Nothing reads the inbox before Task 5, so the change costs no
   client anything.
2. **The loop wakes on any emitted delta but its own,** waits 250ms, and
   recomputes. It also recomputes every second. A wake that arrives while it
   waits or computes is kept: one buffered signal, so a burst costs one more
   recompute, never one per event. Tests shorten both intervals through two
   fields.
3. **"Differs" compares encodings.** The loop keeps the bytes it last sent, and
   sends a delta only when the new encoding is different. The first value it
   computes is always sent. The route always answers a fresh computation.
4. **Every list encodes as an array,** never `null`, even when empty.
5. **The delta is `{"kind": "inbox", "inbox": …}`,** with no session ID.
6. **The browser keeps "Mine" as a filter over the bridge's lists.** The filter
   drops what another owner has, and keeps the order. It stays in `inbox.ts`
   with its tests, and the grouping goes.
7. **An inbox that names an agent the browser has no row for makes it refetch
   the agents,** at most once a second. Until then the ID is not shown.
8. **The browser takes intake from the queue.** Home's needs-you list and the
   sidebar's Pending count read the queue's intake items, so a submission
   appears within a second.

   App's `listPending` refetch stays for the Pending page, which lists every
   submission's detail.

## Contracts

### The inbox (`web/bridge/inbox.go`, Tasks 1 to 3)

```go
// inboxView is the fleet's inbox (P5 F2). Task 4 moves it into the contract
// as contract.Inbox.
type inboxView struct {
	Groups inboxGroups `json:"groups"`
	Queue  []inboxItem `json:"queue"`
}

// inboxGroups are agent IDs, each list in urgency order.
type inboxGroups struct {
	NeedsYou []string `json:"needsYou"`
	Running  []string `json:"running"`
	Ready    []string `json:"ready"`
	Earlier  []string `json:"earlier"`
}

// inboxItem is one entry in the needs-you queue, oldest first.
type inboxItem struct {
	Kind      string    `json:"kind"` // "agent" or "intake"
	AgentID   string    `json:"agentId,omitempty"`
	PendingID string    `json:"pendingId,omitempty"` // replaced in Task 4
	At        time.Time `json:"at"`
}

// inboxDelta is the "inbox" delta on the fleet stream.
type inboxDelta struct {
	Kind  string    `json:"kind"`
	Inbox inboxView `json:"inbox"`
}

// computeInbox applies F2's rules to a snapshot and the intake list.
func computeInbox(agents []AgentStatus, pending []PendingSpawn) inboxView

// Inbox is the fleet's inbox now.
func (f *Fleet) Inbox() inboxView

// On Fleet:
	// inboxWake wakes the inbox loop; one buffered signal.
	inboxWake chan struct{}
	// inboxDelay and inboxEvery are the loop's settle delay and tick:
	// 250ms and 1s; tests shorten them.
	inboxDelay, inboxEvery time.Duration
	// inboxSent is the encoding of the last inbox delta sent (loop only).
	inboxSent []byte

// runInbox is the inbox loop; NewFleet starts it, and it ends with done.
func (f *Fleet) runInbox()
```

## Task 1 — the inbox's rules

**Files:** a new `web/bridge/inbox.go`, and a new `web/bridge/inbox_test.go`.

1. `computeInbox` applies F2's rules.
   - Each agent goes in the first group it qualifies for:
     - needs you, when `Pending` is set;
     - running, when its status is `running`;
     - ready, when it is idle with `ChangedFiles` above zero and no `PRUrl`;
     - earlier, otherwise.
   - Each group is a stable sort by pending kind, then the status rank, then
     the newest `UpdatedAt` first. The ranks are `fleet.ts`'s.
   - The queue is a stable sort, oldest first, of the needs-you agents at their
     `UpdatedAt`, followed by every submission at its `CreatedAt`. Agents are
     listed first, so they win ties.
   - Every list is an array, never nil (decision 4).
2. `Fleet.Inbox` is `computeInbox` over `Snapshot()` and `ws.Pending()`.
3. Port W2's cases to table tests in `inbox_test.go`, over `AgentStatus` values
   built as `fleet.test.ts`'s `mk` builds rows:
   - every case of `groupAgents`' three tests (`fleet.test.ts:267`), with the
     same expectations;
   - `buildInbox`'s merge test (`inbox.test.ts`), oldest first with intake;
   - its owner tests do not move: the bridge has no scope. Task 5 keeps them in
     the browser.
4. Add the cases the browser never had:
   - two agents whose `UpdatedAt` differs only below the second, in either
     order;
   - a tie in both orders, keeping the snapshot's order;
   - an agent and a submission at the same instant, agent first;
   - no agents and no submissions, encoding four empty arrays and an empty
     queue.

**Verify:**

- Mutation check: sort the queue newest first. The merge case must fail. Then

## Task 3 — the loop and the delta

**Files:** `web/bridge/inbox.go`, `web/bridge/notify.go`, `web/bridge/fleet.go`,
and `web/bridge/inbox_test.go`.

1. `NewFleet`:
   - sets `inboxWake` to a channel with a buffer of one;
   - sets the two intervals to 250ms and 1s;
   - starts `runInbox` when `done` is set, as the terminal loop starts.
2. `emit` wakes the loop with a send that never blocks, for every delta that is
   not an `inboxDelta` (decision 2).
3. `runInbox` waits for whichever comes first: a wake, the tick, or `done`.
   - After a wake, it waits `inboxDelay`. Then, on wake or tick, it computes
     `Inbox()` and encodes it.
   - When the encoding differs from `inboxSent`, or nothing has been sent yet,
     it emits an `inboxDelta` and keeps the bytes (decision 3).
   - It returns when `done` closes, including during the delay.
4. Tests:
   - Use a fleet from `testFleet`, with both intervals shortened to a few
     milliseconds before anything is emitted.
   - Read the deltas from `Tail(fleetStreamKey)`.
   - The cases:
     - `TestTheInboxIsSentOnceThenOnlyOnChange`: after a wake, one `inbox`
       delta. A second wake, with nothing changed, adds none.
     - `TestAPendingRequestMovesTheAgentIntoNeedsYou`: a pending request
       observed for an agent, as the classifier's registry hook does, gives an
       inbox delta whose `needsYou` names it.
     - `TestTheTickCatchesAChangeWithNoEvent`: a submission put with
       `PutPending`, with no delta emitted, appears in an inbox delta within a
       few ticks.
     - `TestABurstCostsOneRecompute`: a hundred deltas emitted within the delay
       give at most two inbox deltas. Count the recomputes through a test hook
       on the loop, if timing makes counting deltas unreliable.
     - `TestTheInboxDeltaDoesNotWakeTheLoop`: with the tick set long, one wake
       gives one recompute, not a chain.
     - `TestTheLoopStopsWithTheFleet`: after `Close`, no further inbox delta
       arrives, and the loop's goroutine has returned.
5. Run the tests that read the fleet stream. These are the ones that read
   `fleetStreamKey`: `automation_test.go`, `budget_test.go`,
   `classifier_test.go`, `gate_test.go`, `netlog_test.go`, `reviewfix_test.go`,
   `terminal_test.go`, `usage_test.go` and `watches_test.go`. `sse_test.go` and
   `events_test.go` run too. A test that counts every delta on the stream may
   now see inbox deltas.
   - Where that test is about other kinds, filter out `inbox` there.
   - Where it is about the whole stream, set the fleet's tick long instead.
   - Never stop the loop in production code to suit a test.

**Verify:**
- `go test ./web/bridge/ -count=1 -timeout 20m`. A hang in
  `TestRecipeRunMaxUSDSetsAPausingCapForTheRun` is the known intermittent one:
  rerun the package and record it.
- `go test -race ./web/bridge/ -run Inbox -count=1`, with no data race
- Mutation check: let the inbox delta wake the loop. With a long tick,
  `TestTheInboxDeltaDoesNotWakeTheLoop` must fail. Restore it.
