Marshal TUI · design proposal

Marshal Single Stack

A one-column layout for narrow and half-width terminals. Tool calls are grouped under the narration that explains them, tasks show the agent's progress, and every item can be opened for more detail.

Recommendation in brief

  1. Make the step the main unit of the transcript. A step is one model response: its narration becomes the step's headline, and the tool calls from that response sit indented beneath it. This needs a step ID in the data model. Today narration and tool calls are stored in separate logs and only lined up by timestamp.
  2. Use the todo list to structure the transcript into tasks. Each todo becomes a task header. A task folds to a single line once it is done, so the transcript stays short enough to scan.
  3. Replace five progress widgets with one "now dock" above the input. It shows only work that is currently running, and it uses no rows when idle.
  4. Remove the side rail. Its key numbers move to the status line. Its sections move into a session sheet that opens on ctrl+b. The section renderers can be reused as they are.

02

The stack

The screen is four zones stacked top to bottom, with no side columns. Your eyes stay near the input, so anything live sits just above it. The transcript holds history and stays out of the way until you open something.

transcriptTurn → task → step → tool callFinished work folds up and live work stays open. Scrollable, with keyboard browsing.
now dock0–4 rows: the plan's progress bar, plus any running agents, jobs and watches
inputUnchanged. Approval and question panels still take its place when needed.
statusMode · model · ctx % · changed files · branch (the most useful numbers from the rail)

Principles

  1. Each fact appears in one place. A running tool shows in its step. The dock only repeats it after you scroll away from that step.
  2. Glyphs show state; prose says what is happening. The left column is only state glyphs (⠋ ✓ ✗ ·), so you can see failures by scanning down one column. The headline next to each glyph is the agent's own sentence.
  3. Things shrink as they finish. Running work is open, a finished step reduces to its rows, and a finished task reduces to one line. The final answer is never folded.
  4. Every item has more detail one key away. Every row has outline, steps, full and inspector views, so nothing is hidden for good.
  5. It works from 60 columns up. The right-aligned metadata (owner, duration, counts) is dropped first, then the dock shrinks to one row. Headlines are never cut short to make room for metadata.
03

Steps

A step pairs what the agent said it would do with what it then did. The runner already produces both from the same model response, at runner.go:1346, which stores the narration and then runs the tool calls. The change is to give both the same ID so the transcript can group them.

  • Headline: the first sentence of the narration, in bright text. The rest of the narration sits muted beneath it and folds away at outline density.
  • Glyph: the step's overall state: running, ok, or the worst outcome among its tools. A failed test turns the step's glyph red, so you can spot failures from the top of the screen.
  • Tool rows: indented to column 5, which the code already defines as nestedBodyIndent. The existing row logic (symbolSubject, shellSubject, diff stats, callers) is reused. Repeated reads are merged within the step only.
  • Thinking: appears as a row inside the step ("thought for 3s ▹") instead of a separate box between items.
  • No narration: Marshal writes a headline from the tool calls, in dim italic and labelled inferred, so you can always tell the agent's words from Marshal's. A prompt change (see What changes) makes this case rare.
04

Detail on demand

Instead of a single expand toggle, there are four levels of detail. ctrl+g cycles the default level for the whole transcript, and in browse mode ↵ changes the level for one item. The inspector is a full-screen panel built on the dock's existing FullFrame mode.

05

Progress

The todo list already describes the agent's plan. In this proposal it also structures the transcript. When a todo becomes in-progress, a task header line is drawn. Every step records which task was active when it started. When the task completes, it folds into one line with a summary: steps, tools, edits and time. Tasks you expand stay open.

This gives you the "how far along are we?" answer twice: in the scrollback as a list of finished tasks, and in the dock as a progress bar. With no plan (short turns), there are no task headers and steps sit directly under the prompt.

Folding rules

  • A task folds when it completes, unless it contains a failure that was never fixed, or you expanded it.
  • Plan runs (/sdd) use the same structure one level up: run → plan task → steps. Run events (verify gate, review verdict, commit) become steps owned by the controller.
  • If the agent rewrites its todo list partway through, tasks are matched by ID. Removed tasks keep their history and show "dropped".
06

Ownership

Each step answers who did it. The orchestrator is the default owner and has no label. Any other owner (a subagent, a pipeline role, a custom agent) gets a label when it takes over, and the label is not repeated on every row. This is how chat apps group consecutive messages from the same person.

07

Now dock

The dock replaces renderTurnSpinner, renderTodoPanel, renderLiveStrip, renderActivityLane and renderRunPanel. One function plans its rows, and the same plan is used to both render and measure it. lanePlan already works this way, so the pattern exists in the code.

08

Browse mode puts a cursor on the stack. Typing stays the default. You enter browse mode on purpose and leave with esc. Mouse clicks keep working: each click maps to a step or row ID instead of a range of lines.

Risks

  • Local models that don't narrate. Many small models output tool calls with no text. Inferred headlines cover this, but the transcript will feel less personal with those models. If require is set, it costs a few output tokens per step.
  • Parallel tool calls. A step can run several calls at once. The current single ActiveToolCall becomes a list, which affects the status line and the spinner logic.
  • Render cost in long sessions. The node cache is required. Without it, a tree of hundreds of steps re-rendered through glamour on every spinner frame would be slower than today.

13

Decisions for you

  1. Should finished tasks fold by default? I recommend yes, with ctrl+t to keep them open for the session.
  2. How hard should Marshal push models to narrate? The options are require (a prompt instruction), allow (use narration when present and infer otherwise) or off. I'd default to allow and see how your local models behave.
  3. Which key enters browse mode? shift+↑ is easy to discover but not every terminal reports it. Alternatives are alt+↑, or esc when the input is empty and the agent is idle. esc can't be used while the agent is working, because it cancels the turn.
  4. Should the owner label sit on the right or as a heading? The mockups use a heading line where the owner changes, plus a right-aligned label on single steps. Right-aligned labels are the first thing dropped at narrow widths.
  5. Delete the rail or keep it as an option? I recommend deleting the layout code, since the sections live on in the sheet. Keeping both means maintaining two layouts.
  6. Should P1 ship by itself first? It's cheap and shows whether the single column feels right before the schema work in P2.
