# Cross-device factory working drafts — feature specification

Date: 2026-11-15
Status: implementation specification drafted from the approved [working-drafts design](factory-working-drafts-design.md); implementation plan approved 2026-11-15.

## 1. Outcome and scope

Users can start incomplete manual factory handoffs, autosave them to a project-scoped backend working-draft store, reopen them on another device, and recover offline edits and concurrent conflicts. Field-level conflict resolution allows the user to combine values from both versions and edit the result. An explicit, replay-safe conversion creates an ordinary factory draft; it does not approve or start a run. No MCP or Claude planner integration, simultaneous text collaboration, automatic paragraph merge, automatic draft expiry or multi-user authorization model is added here.

## 2. Data and identity

Each backend working draft has a server-generated random ID, canonical registered project root, `version` (starting at 1), `updatedAt`, lifecycle `editing`, `converting`, `converted` or `deleted`, and the complete **editor input state**. Store title, plan, spec, repo ID, branch/workspace/model/limits overrides, reviewer instructions, CI mode and text, native plus whether it was chosen, implementer auto and no-CI acknowledgement. Store explicit selections as selections: an absent override continues to inherit current settings when eventually converted; do not replace it with a displayed effective value. Permit empty and temporarily invalid fields. Cap title/config and combined plan/spec to the existing factory import limit, with a bounded request envelope; surface over-limit errors without deleting local input. Never store model/provider credentials or environment variables in draft content. Project identity is the server's existing registered project root; browser-generated content cannot move a draft to another project. A user without a selected project may type and save locally, but cross-device autosave begins only after a registered project is selected; display `Only on this device` until confirmed.

Use an independent bridge-owned store under the configured state directory, private to the user (directory 0700, files 0600). Atomic persistence, single-writer ownership, checksums and recovery must detect corruption instead of silently returning an empty draft set. Persist versions, tombstones, mutation IDs, conversion intents and resulting item references across restart. Do not automatically expire or delete drafts, local conflict versions or tombstones. The browser may lose or evict local storage; confirmed backend saves remain authoritative for cross-device access.

## 3. HTTP contract

Use existing authenticated Studio `/api` routes, not the factory journal API or MCP:

- `POST /api/factory/working-drafts` creates a draft using `{projectRoot, requestId, content}`; returns `{draft}`. Reusing the same request ID with identical content returns the original draft; a changed payload conflicts.
- `GET /api/factory/working-drafts?projectRoot=...` lists non-deleted drafts for that registered project, including converted links; `GET /api/factory/working-drafts/{id}` returns full current state. No unregistered project or ID may be used to cross project scope.
- `PUT /api/factory/working-drafts/{id}` takes `{requestId, expectedVersion, content}`. A matching `editing` version durably saves and increments the version; a stale version returns HTTP 409 with current accessible state, without mutation. Identical accepted request replay returns its original result even if later versions exist. Reusing its request ID with different bytes conflicts. Return whether the current state is editing, converting, converted or deleted; stale clients must not resurrect a tombstone.
- `DELETE /api/factory/working-drafts/{id}` takes `{requestId, expectedVersion}`. It records a tombstone and rejects stale versions. A device with unsent edits retains its local copy and offers recovery as a new draft; deletion does not silently discard it.
- `POST /api/factory/working-drafts/{id}/convert` takes `{requestId, expectedVersion, factoryRequest}`. It freezes the precise input version and complete `FactoryCreate` request (including the user-visible resolved configuration and stable factory request ID), then creates or reconciles one ordinary factory item. Return `{draft,item}` when known, or a durable `converting`/uncertain state when the outcome cannot be established. An identical retry returns the same item. A different request for a draft already converting/converted returns its current state and never creates a second item. Reject stale or deleted input and invalid/preflight-failing requests without starting a factory run.

All request IDs have operation and payload hashes; mutation replay is authorized and checked before current-version comparison. IDs are scoped by store/draft and operation, never global across arbitrary users or clients. The server uses the project stored in the draft, not a caller-supplied alternate root. API responses distinguish not found, validation, conflict, unavailable and uncertain; do not return tokens or unrelated project data. The existing single-user API authentication remains in force; multi-user scoping is a later feature.

## 4. Autosave and device recovery

A new project draft obtains a backend ID and version before the UI displays `Saved`. Save changes after a short debounce and serialize writes per draft/device. Keep a durable browser-local record keyed by installation, project, draft and a per-tab editor ID containing the last acknowledged base version, latest local content, outstanding request ID and its exact request body. Write locally before sending; if local persistence fails, surface it and do not claim offline recovery. Display `Saving`, `Saved`, `Offline — changes on this device`, `Conflict`, or an actionable error. A pending network request isn't proof of failure: retry its identical body and request ID before issuing later queued edits. A late response may advance only the acknowledged request/version, never clear later local edits. Avoid storing credentials; explain in UI that plan and specification content is saved on this device and backend.

After reload or reconnect, restore pending data and reconcile with the backend. A different backend version, deletion, or completed conversion never silently overwrites unsent local text. If local storage is unavailable, continue online editing only while visibly reporting that offline recovery is unavailable. Preserve entries until explicit discard or confirmed save/conversion; no automatic cleanup of unconfirmed content. Before navigation/close with unsaved or uncertain edits, retain existing warning behavior where the browser supports it.

## 5. Conflict resolution

On a stale write, retain the device base, local content and latest server content. Show an accessible comparison and an editable combined result, allowing a user to choose local or server values independently for each user-facing field; plan/spec text can be manually edited to combine paragraphs. CI mode plus its text is one field; native plus its chosen flag is one field; repo and project identity cannot be mixed across projects. Start the combined result with the local values and show every changed field and both values; no automatic paragraph merge. Keep both source versions until a conditional save of the combined result is confirmed. If the server advances during review, retain the in-progress combined result, fetch the new server content and repeat comparison against the new version. If deleted or converted, offer to copy the local/combined result into a new working draft, without reverting the server lifecycle.

## 6. Conversion and crash recovery

Display the values that will be submitted, including the effective inherited defaults, and the current project settings version before conversion. The user explicitly confirms creating a factory draft. Resolve and preflight using the existing factory path; bind the confirmed effective configuration and working draft version to the durable conversion intent. If defaults change between display and submission, reject and require a refreshed review rather than creating with different values. Serialize competing conversions per working-draft ID. Persist a `converting` intent containing a factory request ID and exact frozen FactoryCreate **before** calling `FactoryAPI.Create`; disallow autosave/delete while conversion is in flight, retaining any pending device changes locally.

If factory creation fails with a confirmed validation/preflight error before an item is journaled, return the working draft to `editing` with the error and keep its contents; a subsequent attempt uses a new conversion request ID. If a response is lost or the bridge stops after intent, replay the exact frozen factory request using the same factory request ID. The factory's existing `priorRequest`/`CreateResolved` replay path determines whether it already created an item; never generate a second factory ID. An internal conversion entry point must store the frozen, already-resolved configuration without re-inheriting values from later project defaults; it must still enforce factory validation and preflight for an operation not yet journaled. Only mark `converted` after the item identity is durably associated with the working draft. If the factory journal is corrupt, unavailable, or the outcome otherwise cannot be established, stay `converting`/uncertain and present the state; do not retry as a new create. A restart reconciles unfinished conversion intents before accepting another conversion for that draft. Keep the factory journal and working-draft store separate; this is reconciliation across two durable stores, not an exactly-once transaction.

Once converted, the working draft becomes read-only with a link to the factory item. If a device has later unsaved edits, offer to create a new working draft from them; do not mutate the factory item. The factory item remains unapproved, and existing checks and ownership protections remain unchanged.

## 7. Acceptance

Test backend save and replay, storage permissions, restart, version conflicts, delete/conversion races, invalid fields and corruption with fake clocks and isolated temp stores. Test UI recovery on two isolated browser contexts sharing the backend, offline/reconnect, out-of-order responses, storage failure, field-level selection and editable plan/spec, repeated conflicts, and private/offline draft creation. Exercise crash and lost acknowledgement at each boundary: before intent, after intent, after factory journal append, after association and after response. Prove simultaneous conversions yield one item; a validation failure yields none; old factory create/replay and approved snapshots are unchanged. Test current inherited settings and a default change during conversion review. Verify phone (390px) and desktop flows, keyboard access and mobile layout without horizontal overflow. Test fixtures own their endpoints and never contact real providers or credentials.
