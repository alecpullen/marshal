# Marshal agent Studio integration: specification

Date: 2026-11-16

Status: specification of the [approved design](marshal-agent-studio-integration-design.md). See the [implementation plan](plans/2026-11-16-marshal-agent-studio-integration-plan.md).

## Scope and existing behavior

Make current-project factory read access automatically available to a Marshal session in the TUI or Studio and to factory implementer/reviewer sessions, without manually configuring an MCP server. Provide user-configurable project defaults and individual session/worker overrides for access to the existing factory MCP operations. A built-in integration identifies the selected Studio instance and originating session, uses the existing factory service and journal, and degrades gracefully while unavailable.

The implemented `web/bridge` MCP endpoint already exposes `factory_projects`, `factory_list`, `factory_get`, `factory_create_draft`, `factory_update_draft`, `factory_approve_and_queue`, and `factory_answer_question`. It authorizes registered client tokens against project grants and checks them at mutation time. Current external-client `user_directed` is an assertion by the client, not independent proof. Marshal starts only configured MCP servers; its normal remote client validates HTTP(S) endpoints, while the local daemon profile listens on a Unix socket. Existing tokens identify MCP clients, not individual Marshal sessions. None of those facts establish an automatic built-in connection today.

Prototype actual MCP behavior first. A built-in client may supply a session-specific transport/authentication source to the existing MCP client without writing an MCP server entry to user config. For local Studio, use the already authenticated owner-only daemon socket and a narrowly scoped, per-session enrollment/attestation path; do not expose a new unauthenticated TCP listener or globally relax remote MCP URL validation. For a configured remote Studio, require an explicitly selected, authenticated endpoint and enrollment; never forward local credentials to a different instance. Bind enrollment to the actual daemon-issued session, selected instance, canonical project identity and, for a worker, its saved factory item/role. If a binding cannot be verified, show unavailable and grant no automatic read. When the running worker is in a different execution environment, its project mapping must use the trusted owner/session association, not a host path supplied by the model.

If a prototype proves MCP cannot satisfy session identity, permission enforcement or lifecycle, write a concise evidence report and implement a thin Marshal-specific adapter to the same service and policy. The adapter must provide the same user-visible capabilities and tests, without embedding the factory controller into `internal/` or making `web/` import `internal/`. Unsupported remote or external-worker cases are labeled; never claim a connection or permission that has not been verified.

## Discovery and access

For an unambiguous local registered project, discover and bind the current instance and its opaque project ID automatically. Project identity derives from the repository root and the trusted session/worker mapping; do not expose raw host paths to the model. Multiple possible instances or project mappings require the user's selection, which is persisted as a preference for that scope. A missing, offline, ambiguous or unsupported service does not block session startup; UI and tool results explain the status and preserve last-known state as stale. Reconnect or a changed session/instance identity requires revalidation; an old token must not silently bind to a new session.

Default the built-in principal to read for its current project; default create-draft, edit-draft, answer-question and approve-and-queue to off, and approval authority to none. Users may change project defaults or override any field for a particular session or worker, including disabling read. Explicit false differs from inherit. A worker inherits project defaults unless individually overridden; it must not inherit broader rights merely from its factory role. Resolve and enforce effective permissions on every call under the existing policy/admission lock, including immediately after revocation. Preserve existing external MCP grants and identity semantics unchanged. Existing `Autonomous` settings, project trust, worker role or ability to read never imply write permission.

Authorization must identify both the authenticated connection and the real session. Do not allow the model or MCP tool arguments to choose its session ID, worker role, project scope, or permissions. Keep credentials in the trusted integration transport, not prompts, model-visible tool results, logs, project files or child-controlled environment variables. A bearer credential alone proves only possession; only a trusted session-binding mechanism may attach session provenance. Deny or return unknown when that binding cannot be verified, including if the service restarts or a worker's ownership changes. Apply the parent's authority ceiling to any child agent inheriting these tools; it cannot claim a stronger identity or authority.

## User direction and operation semantics

The user can enable `user_directed` or standing approval authority; standing is off until explicitly enabled and remains revocable. The integrated session may record verified user direction only when a trusted, current session interaction binds an explicit user request to the exact operation and target. Normal natural-language text cannot be treated as cryptographic or machine-verified consent merely because the model asserts it. Reuse an existing authenticated user-action/approval receipt when available. If no reliable receipt exists, use the existing interaction approval flow for that operation, without requiring a separate Studio click when a prior trusted receipt already covers it. A model-provided `userApproved` value, stale or unrelated request, and external MCP's client assertion alone are not such receipts. Provenance distinguishes verified user direction, client assertion, standing authority and delegated planner where applicable.

Use the existing factory controller, per-action grants, request IDs, version checks, independent review and recovery gates. Lost responses are reconciled using the existing request identity; never blindly duplicate a mutation. An implementer or reviewer can use permitted actions, but its role and actor are recorded and cannot replace the factory reviewer. No merge, arbitrary shell, permission administration or other operation absent from the existing MCP surface is introduced. Do not grant additional access to external MCP clients or automatically create subsequent factory runs.

## Surfaces and evidence

Expose connected instance, project, state, last verified time and effective permissions in the shared session experience, on mobile and desktop, and an equivalent TUI settings surface. Project settings control project defaults; session/worker controls expose individual overrides, inheritance, revocation and instance selection. Preserve existing external MCP client management. Only users using existing authenticated settings surfaces can change grants. Selection and grant changes are versioned, and stale concurrent edits conflict rather than erase another change.

Automated tests use isolated sockets, credentials, deterministic models and disposable repositories, not developer config, ambient services or live tokens. Exercise real Marshal session → built-in transport → actual MCP endpoint → factory service for TUI-origin, Studio-origin and factory worker sessions; verify defaults, individual isolation, source project/instance, revocation, stale versions, child authority and truthful provenance. Cover local socket, explicitly configured authenticated remote, absent or ambiguous daemon, restart, request replay and lost responses. Test direct natural-language user requests with and without a trusted action receipt. Confirm independent factory review and existing external MCP grants stay unchanged. Record actual live MCP/remote environment and mobile/TUI walkthrough coverage separately.
