The framed console, with progress cards

Live work's download, transfer, test and custom progress cards move into the box's running section. Each card is one row with a measured bar. History marks todo progress with a plan line and a numbered tag on each todo's first step. Ctrl+T cycles the plan between stacked, split and folded.

  • LayoutConsole: history only grows; everything live is in one framed box above the input.
  • Plan modesCtrl+T  stacked → split → folded
    [tui.dock] layout sets the start; split needs about 90 columns.
  • Progress in historyA plan line where the list changed, plus ▸ N/M on the first step of each todo. No dividers.
  • Progress widgetsLive work's cards, one row each, with the bar the spec drew but the TUI never rendered.

  • Plan lines sit where the agent updated the list. Three appear here, one per update.

  • Measured work shows a thin bar in its kind's colour, the percentage and the most useful measurement.
  • Tests show counts and never a percentage, because Go's JSON output has no suite total.
  • The subagent shows its latest activity.
  • The top border carries the turn timer and both keys.

The truthfulness rules are unchanged. There is no bar without a reported total, and a phase percentage is labelled “of phase”. A stale measurement hides rate and ETA and shows its age. A process still running at 100% says so.

Teaching the agent

The model sees progress in the tool schemas (profile, source, title), but nothing in its context describes the @@marshal-progress/v1 record. It can choose a profile, but it cannot write its own download, transfer or custom producer without first finding docs/live-work/.

Proposal: a built-in progress-reporting skill with the record format, its limits and the three example producers. It loads only when relevant, so the cached prompt prefix is unchanged. The progress parameter gains a one-line pointer to it.

Answers

  1. Ctrl+T and the Tasks panel: fine for now. The keyboard shortcuts will be reworked later, so none of these keys are fixed.
  2. Failed background work: a red completion event for now. Expanding it, like any other entry, shows a fuller issue report.
  3. The progress-reporting skill: yes.
  4. Consolidated spec: yes. See docs/tui-simplification/feature-spec.md.
