Marshal · web UI proposal

Marshal Web Studio

A self-hosted home for your agents: launch them, watch them work, review and ship what they produce, and design the workspaces they run in. The transcript follows the same rules as the single-stack TUI, with web styling on top.

OverviewWhat's builtSharing logic with the TUIPages and optionsWork outlinesMore ideasRoadmapDecisions

In short

  1. The backend is further along than the web UI. The bridge already runs containerized agents in isolated worktrees, takes requests from issues and MCP clients, and ships work through a verify gate to a pull request. Marshal's ACP server also exposes skills, plugins, memory, plan runs and swarms. The web UI uses about half of this.
  2. Keep the TUI's transcript logic by sending its view model over ACP. The browser renders the same turn → task → step tree that tui/stack builds. It doesn't re-implement the grouping in TypeScript.
  3. Workspaces are the biggest new piece. Today a project can only name a container image. A workspace template would add toolchains, packages, shared files, read-only library mounts, secrets, network rules, resource limits and a setup script, and could be reused across projects.
  4. The suggested build order: design system and transcript parity, then the session workbench and review, then runs and settings, then workspaces, then operations (notifications, triggers, terminals, multiple users).

02

What's built

The code lives in two places. web/bridge is a Go server built from the standard library only, and web/ui is a Svelte 5 single-page app. The bridge runs marshal acp agents, either as child processes or in containers, and talks to them over ACP. Each agent below falls into one of four states.

in web UI works in the browser todayAPI only the bridge or ACP supports it, no screen yetpartial some pieces existnew not built anywhere

in web UI

  • Fleet dashboard grouped by project, with agents that need you listed first
  • Warnings for unavailable or untrusted projects, leftover worktrees, and non-isolated agents sharing a checkout
  • Attention list to approve, deny or answer without opening the agent
  • New agent with an optional isolated worktree; start from a GitHub or Gitea issue
  • Chat session with streaming text, reasoning, tool cards, approval and question dialogs, six modes, steer, cancel
  • Diff view, merge, discard, patch download
  • Ship flow commit, run the verify gate, push, open a PR; override a failed gate with a reason
  • Sessions panel to list, create, load and delete sessions per project
  • Projects panel to add and remove project roots
  • MCP clients with tokens shown once and agents scoped to their client
  • Intake queue to approve or deny agents requested by MCP clients or issues
  • Activity feed (audit log), disk usage and prune
  • Token login and live updates over server-sent events (SSE)

API only

  • Container runtime with Docker or Podman, per-agent volumes, resource caps, an allowlist for passed-through environment variables, and shared bare mirrors
  • Per-project image read from the image field in .devcontainer/devcontainer.json
  • Credentials store and forge adapters (GitHub, Gitea)
  • Issue poller that turns watched issues into intake requests
  • Fleet limits and a spawn queue
  • /mcp endpoint so other tools can start and drive agents
  • ACP: skills (list, load, install with preview, remove)
  • ACP: plugins (scan, install, remove) and memory (list, delete, set confidence)
  • ACP: plan runs sdd_start/status/answer, swarms swarm_start/status, agents roster
  • ACP: slash commands (command_list, command), verify, commit, worktree prune, resume

partial

  • TUI-style transcript (steps, owners, tasks, receipts). The engine builds them, but ACP doesn't send step, owner or task IDs, so the web shows flat tool cards
  • Settings for providers, model presets and role routing exist in the TUI (/settings, /connect), but there's no ACP method to read or write them
  • Usage turn_metrics records tokens and cost per turn; the bridge only reports context % and changed files
  • Workspaces are an image plus resource caps; there are no toolchain layers, shared files or network rules
  • Single operator (DefaultOwnerID); the data model has room for owners, but there are no users

new

  • Workspace templates and designer covering toolchains, packages, shared volumes, library mounts, secrets, network rules and setup scripts
  • Terminal attached to an agent's container, and preview of ports it serves
  • File browser and editor for the agent's worktree
  • Screens for plan runs and swarms
  • Scheduled and triggered agents (cron, webhooks, issue labels beyond the poller)
  • Notifications (web push, email, ntfy)
  • Budgets and cost caps
  • Multiple users, roles and teams
  • Rewind, history and export in the browser

Two limits are deliberate and should stay. A project can't be trusted from the browser; you open it once in the TUI. And the default agent image includes no language toolchain, so the verify gate reports "skipped" instead of guessing. Workspaces are where those toolchains would be declared.

03

Sharing logic with the TUI

You want the same core UI logic as the TUI. That logic is tui/stack: a structure-only view model that groups the transcript into turns, tasks, steps and tool rows, and works out folding and receipts. web/ must stay standard-library only and can't import Marshal's Go packages. So the logic has to travel as data. There are three ways to do that.

How it worksUpsideDownside
A · Send the view model recommendedmarshal acp runs the same stack.Build and sends a _marshal/stack snapshot when the client attaches, then patches keyed by node ID. The browser only renders.One implementation, so the TUI and web can't drift. The node IDs already exist. Density and folding stay per client.stack must move out of internal/app/tui (to internal/viewmodel) so ACP can import it without depending on the TUI. Needs a patch protocol.
B · Send structured eventsACP adds stepId, actor, todoId and toolCallId to its current updates, and TypeScript re-implements the grouping.A small change to the protocol. Other ACP clients get richer events too.Two copies of the grouping rules (heuristic steps, re-binding, unresolved failure). Shared golden fixtures would be needed to keep them in step.
C · BothDo B first, since other clients benefit, then A as an optional snapshot for clients that want it.Third-party clients and the web UI are both served.The most total work.

What maps across directly

  • Transcript follows the same rules: a headline from narration, inferred headlines in italics, owner and duration on the right, tasks that fold, a turn receipt, the four density levels and the inspector.
  • The now bar becomes a strip pinned above the composer, with the same rows: plan progress, live mirror, agents, jobs.
  • Browse mode keeps its keys (Esc, j/k, i, y, o), so the browser works from the keyboard like the terminal. The mouse adds hover and click.
  • Session sheet sections (context, changes, usage, skills, rules, fleet, repo) become the workbench tabs and the project overview. The Section data can be sent the same way.
  • Visual identity: the web UI currently uses a cool blue accent, while the TUI uses Warm Sunset (coral, violet, gold). The mockups adopt the TUI palette so the two read as one product.

06

More ideas

Agent work

  • Model bake-off. Run one task on three models in parallel, then compare diff, gate result, cost and time side by side.
  • Fork from a step. Start a new agent from any step of an old one, with its worktree and context at that point.
  • Hand off between TUI and web. "Open in terminal" prints marshal --resume <id>, and the TUI gets "open in browser". Both use the same session DB.
  • Replay. Scrub through a finished run's steps with the file state at each point.
  • Watch monitors. A UI for the TUI's background watches and jobs.

Workspaces and safety

  • Network inspector. See every host an agent contacted, and allow or deny new ones on the spot.
  • Workspace diff. Compare two template versions and see which agents would change.
  • Snapshot to template. Turn a container you set up by hand into a reusable template.
  • Secret-use log. Record which agent read which secret, and when.
  • Safe pre-approvals per workspace. For example, any go test is allowed inside go-service.

Teams and operations

  • PR review bot. A forge webhook starts a read-only reviewer recipe on new PRs.
  • CI fixer. A failed check on a branch starts an agent in that branch's workspace.
  • Shared memory across projects, with confidence and provenance shown.
  • Eval dashboard. Pass rates of recipes and models over time, built on the eval scenarios that already exist.
  • Status page. A read-only link to a run for people without an account.

Decisions

  1. Shell: A (rail + agent sidebar), B (top bar + palette) or C (three panes)? I'd go with A.
  2. Home: A (inbox), B (board) or C (live wall)? I'd go with A, with C as a toggle.
  3. Session: A (focus + inspector), B (workbench) or C (editor)? I'd go with B, plus a focus toggle that collapses the workbench (A). C could come later.
  4. Review: A (PR style) or B (by step)? I'd go with A, with B as a toggle.
  5. Runs: A (stage lanes), B (graph) or C (timeline)? I'd go with A, with C as a tab, and B once runs have dependencies.
  6. Workspaces: A (layer builder), B (form + source) or C (gallery)? I'd go with C for the list, A for the editor, and a B source toggle.
  7. Sharing logic with the TUI: send the view model (A), structured events (B), or both? I'd go with A.
  8. Palette: adopt the TUI's Warm Sunset palette in the web UI (as mocked), or keep today's cool blue?
  9. Hosting: stay single-operator for now, or plan for multiple users from W1? Multiple users affects auth, secrets and every list page.
