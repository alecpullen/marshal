# W5.5 · UI: terminal, preview, recipes, schedules, notifications, memory, status — implementation plan

**Spec:** [`docs/web-studio/specs/2026-10-03-w5-automations-and-ops-design.md`](../specs/2026-10-03-w5-automations-and-ops-design.md) §6.1, §6.2, §6.4–§6.6
**Execution:** inline, task by task, with `marshal-executing-plans`.
**Track:** UI. See [`../README.md`](../README.md) for both tracks.
**Runs after:** [W4.5](2026-10-03-w4-5-ui-network-projects-plan.md) (previous UI plan) and [W5.3](2026-10-03-w5-3-bridge-recipes-schedules-plan.md) (this phase's backend gate), with everything those depend on.
**Base:** a branch containing every plan listed under Runs after. Names from earlier phases are
as their plans define them.
**Plan slug:** `w5-5-ui-ops`. Commit each task as `w5-5-ui-ops: task N — <title>`.

## Goal

This plan adds:

- the dock's Terminal and Preview tabs, and Test shell in the designer;
- Recipes in the Library and on New agent;
- Schedules;
- browser notifications and outbound webhook settings;
- memory scopes and suggestions;
- status links.

## Non-goals

- Automations pages, inbox drafts and "Request review bot" (W5.6).

## Assumptions

The bridge routes from W5.2–W5.3:

| Area | Routes |
|---|---|
| Terminals | `/api/agents/{id}/terminal…` and `/api/workspaces/{name}/shell…` |
| Preview | `/api/agents/{id}/preview/{port}` |
| Recipes | `/api/recipes…` |
| Schedules | `/api/schedules…` |
| Notifications | `/api/notifications…` |
| Status links | `/api/status-links…` |
| Memory | `GET /api/library/memory?scope=`, `GET /api/library/memory/suggestions`, `POST /api/library/memory/{id}/promote` (W5.3 Task 6) |

The W2.2 dock renders Terminal and Preview as disabled tabs.

## Task 2: Terminal tab and Test shell

**Goal:** a working Terminal tab with replay, hold state and hand-back,
plus Test shell in the designer (spec §6.1).

**Files:**
- `web/ui/package.json`: add `@xterm/xterm`, `@xterm/addon-fit`
- `web/ui/src/lib/dock/TerminalTab.svelte` (new), `Terminal.svelte` (new), `TerminalTab.test.ts` (new)
- `web/ui/src/lib/dock/Dock.svelte` (enable the tab)
- `web/ui/src/views/workspaces/Designer.svelte` (enable Test shell)
- `web/ui/src/lib/fleet.ts` (the `hold` delta)

**Steps:**

1. Install the packages with
   `npm install @xterm/xterm @xterm/addon-fit`, and import the xterm CSS
   in `Terminal.svelte`.
2. `Terminal.svelte`. Props: `{open: () => Promise<{tid; eventsUrl; inputUrl; resizeUrl}>, onClose}`.
   - Create `new Terminal({fontFamily: 'Geist Mono Variable', theme: {…tokens}})`.
   - Fit it with `FitAddon`.
   - Stream output through W4.4's extended `connectSSE` with `url`,
     decoding base64 and writing to the terminal.
   - `onData` posts base64 input; `onResize` posts the size.
   - On exit, show "process exited (code)".
3. `TerminalTab.svelte`:
   - In select mode, when the node is a shell-family tool row, the top
     pane shows "Replay of <command>" with the full output from W2.2's
     node cache (`InspectTab`'s data).
   - Below it, an **Open shell** button mounts `Terminal` with
     `openTerminal(agentId, {cols, rows})`.
   - The strip shows "agent paused · Hand back" while the fleet row's
     `held` is true, with a 2-minute countdown from the last input. Hand
     back calls `terminalRelease`.
4. In `fleet.ts`, a `hold` delta sets `row.held` and `row.heldBy`.
5. In `Dock.svelte`, remove `disabled` from the Terminal tab. The
   collapsed strip's Terminal badge shows unread output while the tab
   isn't visible.
6. In `Designer.svelte`, enable **Test shell**. It opens a modal with
   `Terminal`, using `openWorkspaceShell(name)`.
7. Tests, mocking `@xterm/xterm` with `vi.mock` and `fetch`:
   - typing posts base64 input;
   - output events are written;
   - the hold strip shows and Hand back calls release;
   - replay shows the node output;
   - Test shell opens with the workspace route.

**Verify:**

```bash
cd web/ui && npx vitest run src/lib/dock/TerminalTab.test.ts && npx svelte-check
```

3. Enable the tab in `Dock.svelte`.
4. Tests: the port list from a doc fixture; open sets `src`; the
   no-ports hint.

## Task 4: Recipes — Library tab and New agent integration

**Goal:** Recipes in the Library (list, edit, run), and a Recipes tab on
New agent that fills the chips and the prompt (spec §6.2).

**Files:**
- `web/ui/src/lib/library/RecipesTab.svelte` (new), `RecipeEditor.svelte` (new), tests
- `web/ui/src/views/Library.svelte` (add the tab; route `#library/recipes`)
- `web/ui/src/views/NewAgent.svelte`, `NewAgent.test.ts`, `web/ui/src/lib/newagent/newAgent.ts`

**Steps:**

1. `RecipesTab`:
   - A list of title, kind, mode, built-in badge and limits.
   - **Run** opens a modal with a project select and the recipe's inputs
     (required ones marked), then calls `runRecipe` and navigates to the
     agent.
   - **Edit** is unavailable on built-ins; they offer **Copy** instead.
2. `RecipeEditor`:
   - name, title and description;
   - kind and mode selects;
   - a workspace select (W4.4) and the routing chip (W3.4);
   - an inputs table;
   - a prompt textarea that highlights `{{name}}` tokens;
   - limits;
   - an output select.

   It validates that every `{{x}}` is declared, then saves.
3. New agent, Recipes tab: picking a recipe sets the mode, workspace and
   routing chips, fills the prompt with the template, and shows input
   fields above the prompt.
   - On spawn with a recipe selected, call `runRecipe` instead of
     `spawnAgent`, so the limits apply.
4. Tests:
   - the editor rejects an undeclared placeholder;
   - run posts the inputs;
   - picking a recipe on New agent sets the chips and calls `runRecipe`
     on submit.

**Verify:**

```bash
cd web/ui && npx vitest run src/lib/library src/views/NewAgent.test.ts && npx svelte-check
```

## Task 5: Schedules

**Goal:** a Schedules view under Watches, with a cron helper (spec §6.2).

**Files:**
- `web/ui/src/views/Schedules.svelte` (new), `Schedules.test.ts` (new)
- `web/ui/src/lib/schedules/cron.ts` (new), `cron.test.ts` (new)
- `web/ui/src/views/Watches.svelte` (tabs: Watches | Schedules), `routes.ts` (`#watches/schedules`)

**Steps:**

1. `cron.ts`:
   - `describe(expr)` gives human-readable text, covering the common
     shapes: every N minutes, hourly at :MM, daily at HH:MM, weekdays at
     HH:MM, weekly on <day> at HH:MM. Anything else falls back to the raw
     expression;
   - `nextRuns(expr, from, n)` mirrors the Go parser's semantics (W5.3
     Task 3) for preview purposes;
   - `PRESETS`.

   Tests compare against the Go table cases, copied as fixtures.
2. `Schedules.svelte`:
   - A table of name, recipe, project, `describe(cron)`, next run, last
     result, and an enabled toggle.
   - **Run now** and **Delete**.
   - The form has name, recipe, project and the recipe's inputs, plus the
     cron with presets, a raw input, and a "next 3 runs" preview.
3. Tests: describe for each preset; nextRuns; the form posts; the
   enabled toggle saves.

**Verify:**

```bash
cd web/ui && npx vitest run src/lib/schedules src/views/Schedules.test.ts && npx svelte-check
```

## Task 7: Notifications

**Goal:** browser notifications for fleet events, and the outbound
webhook settings (spec §6.4).

**Files:**
- `web/ui/src/lib/notify.ts` (new), `notify.test.ts` (new)
- `web/ui/src/views/settings/Notifications.svelte` (new), tests
- `web/ui/src/App.svelte` (wire `notify` to the fleet store)

**Steps:**

1. `notify.ts`:
   - `loadPrefs` and `savePrefs` use `marshal.ui.notify`, in try/catch,
     holding a map from event to boolean (default all on);
   - `maybeNotify(delta, prefs, visible)` maps fleet deltas to the events
     `needs_you`, `run_finished`, `budget`, `automation`, `watch_fired`
     and `network_block`, matching W5.3 Task 4's mapping. It returns a
     notification `{title, body, url}` only when `!visible` and the
     preference is on;
   - `show(n)` uses `new Notification(title, {body})`, whose click
     focuses the tab and navigates to `url`.
2. In `App.svelte`, the fleet delta handler calls `maybeNotify` with
   `document.visibilityState === 'visible'`.
3. `Notifications.svelte`:
   - a permission state, with a **Request permission** button;
   - per-event toggles;
   - a webhooks list and add form (URL, secret ref select from W4.5's
     secrets list, events), with a **Test** button;
   - it lives under Settings → Notifications.
4. Tests:
   - `maybeNotify` for each delta kind, and suppressed while visible;
   - prefs persist;
   - the webhook form posts;
   - the permission request (mock `Notification.requestPermission`).

**Verify:**

